No Database, No Problem: A Chat Platform on Pure Redis

Shoan Bhatambare · 4 min read · Handwritten

Every app needs a database. SQL, NoSQL, pick your poison. Conversatio[1] uses none. The users are ephemeral, the conversations are ephemeral, so naturally the database is ephemeral too. Redis holds everything, and it forgets just as quickly. This went against everything I was taught. Which made it worth trying.

Why no database?

On Conversatio, ephemerality is a feature and not a workaround. Sessions live as long as their user does. DMs auto-expire in an hour. Match rooms come live with the kickoff and die with the final whistle. There is no archive to query, no profile to retrieve. The product is the present moment. Persistence would be a bug.

In comes Redis, a speed demon cache which doubles as a database.

Two Alberts walk into a lobby

Ephemerality works for DMs and events. Public rooms break it by keeping past conversations for future ones. While the rooms persist, the people in them don't. So names recycle. Which Albert wrote e=mc²? Which one called you a moron? A #Tag, covered in the last post, fixes the human side. The race condition fixes the machine side.

Two clients log in as "Albert" the same millisecond. Without a transaction, both win. HSETNX usernames {name} {sessionId}. Set if not exists. One round-trip, atomic, no lock. The first write claims the name; the second gets back zero and tries again with an alternative name.

Sessions are just TTLs

Stop typing → you disappear. Every session is a Redis hash session:{sessionId} with a 15-minute Time-To-Live. The deadline is cast but not in iron. Every message resets the clock. Lurk past 14 minutes, you turn to ash. Send a "Hey", you live another 15.

So you sent that 'Hey'. What now?

Once you manage to get through the door, the gatekeeper at Conversatio's office has some questions for you. He hopes you brought your ID to make sure you belong in the first place. Confirming that your ID is legit and your right to speech still holds, he starts checking the message. He has to be thorough so he quickly makes sure it follows company policy along with any other special ink requirements. The message then enters the data room and while our AI hoover makes its way to do a check, it is copied over to the recipients as well.

Decoded: gatekeeper is the rate limiter, the ID check is fetchSessionAndBumpTTL, the policy is layer-1 regex, the ink is link classification, the data room is a Redis sorted set, the hoover is async OpenAI moderation[3], the recipients are the Socket.IO[4] room:message broadcast.

Sleight of hand

Remember "every message resets the TTL"? Pair that with Redis pipelines and we've got ourselves a neat little two-handed trick: session revalidation + TTL bump in one round-trip. 

// Pseudo: HGETALL + EXPIRE pipelined
const [session] = await redis.pipeline()
  .hGetAll(`session:${sessionId}`)
  .expire(`session:${sessionId}`, 900)
  .exec();

Conversatio's UI feels instant because of optimistic rendering with tempId reconciliation. Client renders the message right away; server acks with a permanent seq.

While this is going on, our AI hoover is hoovering away in the server room.

WOOP WOOP! THAT'S THE SOUND OF THE POLICE

Overseeing messages and maintaining the vibe of rooms is paramount. ConversatioPD runs two units. The bouncer at the door: a regex frisk, sub-millisecond, blocks the obvious before anyone gets in. The plainclothes detective: slower, smarter, expensive AI review that walks the room after the fact and taps shoulders when something off slipped past. The bouncer runs in real-time. The detective catches up later.

The bouncer (layer 1): synchronous regex, sub-millisecond, runs before storage. Catches the obvious. 10 rejects in 60 seconds → escalating mute.

The detective (layer 2): OpenAI moderation, fire-and-forget after broadcast. Verdict cached in Redis by text hash to never review the same message twice. Flag → server retracts the message from every connected client via mod:layer2:retract.

Disclaimer: Conversatio has a fail-open policy. Moderation outages cannot take the chat down.

Sacrifices on the old town road

This design produces a present but fragile system. It gives up reliability and peaceful sleep for simplicity and tightness. We don't anticipate serving a million users any time soon, so we sized the ceiling for the load we'd actually see, not the load we'd brag about.

In a single Redis node, the biggest constraint is memory. We knew this, and even so, Conversatio is sized for thousands of users.

Some other tradeoffs included keyspace notifications[2] not being portable. Render Key Value and Upstash mute the events the expiry listener depends on. The fix is a fallback sweeper polling loop. Whichever fires first wins.

If it's working, it's working. No analytics, no audit log, no "what did we ship last quarter." Ephemeral by design means ephemeral for the operator too.

Designed to forget

Walk into Conversatio tomorrow and the conversation you had today is gone. The username you picked is up for grabs. The match room you cheered in has long since closed. None of this is a bug; all of it is the feature.

Ephemeral by design means the system has to earn each second it stays alive. Every message is a small bet that something matters enough to keep around for fifteen more minutes. Most bets lose. That's the point.

Most production systems hoard. They keep everything because deletion is scary and storage is cheap. Conversatio forgets on purpose, and the forgetting is what makes it work. The constraint became the design. Every piece of state had to justify itself, every subsystem had to fit in fifteen minutes, and the system fits in your head because it has to.
